Label: wayfinder:map

## Destination

A technical architecture spec for the Wake Mate MVP: backend/storage/auth stack, the alarm-sharing (Share) flow, and the concrete data model — iOS-only, sized so a dev (or Claude Code) can start the 4-week testable prototype build directly from it.

## Notes

Domain: mobile social-alarm app. Every session should read `CONTEXT.md` (repo root) for settled vocabulary (Alarm vs Alarm Call, Share, Friend Connection, Queue, Library, Auto-play/Library Mode) before working a ticket. Call the `grilling` and `domain-modeling` skills whenever a ticket touches domain vocabulary or introduces a new concept.

## Decisions so far

- [Friend connection model](issues/01-friend-connection-model.md): Mutual acceptance required (Facebook-friend style, not one-directional follow).
- [Alarm vs Alarm Call terminology and reuse](issues/02-alarm-vs-alarm-call-terminology-and-reuse.md): Split "Alarm" (schedule) from "Alarm Call" (audio); one Alarm Call can be Shared to many friends and reused across a recipient's own Alarms.
- [Received queue & playback mechanic](issues/03-received-queue-playback-mechanic.md): Users can have multiple independent Alarms, each with its own locked FIFO Queue and an Auto-play/Library-override Mode that resets on new arrivals; played Alarm Calls auto-save to the Library.
- [Empty queue fallback sound](issues/04-empty-queue-fallback-sound.md): Falls back to a bundled default alarm tone when Queue and Library are both empty.
- [\"Alarm discovery\" scope clarification](issues/05-alarm-discovery-scope-clarification.md): Means people search (folds into friend-discovery ticket), not content browsing.
- [iOS alarm reliability research](issues/06-ios-alarm-reliability-research.md): Feasible via Apple's AlarmKit (iOS 26+) — short teaser alert fires reliably even through force-quit/silent mode, full Alarm Call plays in-app on launch; requires ticket 03's queue to re-schedule the wake trigger on every head change, no change to the locked-queue/auto-play model itself. Surfaces a new open question: minimum supported iOS version (AlarmKit needs 26+).
- [Backend/storage/auth stack survey](issues/08-backend-storage-auth-stack-survey.md): Surveyed Firebase, Supabase, AWS Amplify, and a custom Node/Postgres/S3 backend — Firebase recommended for the 4-week build (native Swift SDK + Sign in with Apple + zero-setup FCM push, ~$0/mo at this scale); final choice deferred to ticket 09.
- [Analytics/crash reporting tool](issues/12-analytics-crash-reporting-tool.md): TelemetryDeck for analytics (always); Sentry for crash reporting (concretized once ticket 09 picked a non-Firebase backend).
- [Mobile client framework](issues/07-mobile-client-framework.md): Native SwiftUI, not React Native/Flutter — team has zero prior experience in any of Swift/RN/Flutter (no familiarity edge either way), Android is deferred so cross-platform's shared-codebase payoff isn't live yet, and dedicated research found no mature RN/Flutter bridge to AlarmKit (best candidate is pre-1.0, ~2 months old), carrying open-ended structural risk against the 4-week soft timeline.
- [GDPR technical requirements research](issues/14-gdpr-technical-requirements-research.md): Temporary cloud copy of a shared Alarm Call deleted after 48 hours (or on confirmed recipient download, whichever is sooner); raw voice audio isn't Art. 9 special-category data absent voice-ID processing; TLS 1.2+/AES-256 at rest; consider EU-region hosting to avoid cross-border-transfer complexity. Concrete policy locked in ticket 15.
- [Backend/storage/auth stack decision](issues/09-backend-storage-auth-stack-decision.md): Supabase (Auth + Postgres + Storage + Edge Functions) locked, switching from ticket 08's Firebase recommendation — cheap/easy (no forced billing, no proprietary data model) outweighed 4-week build speed for this solo-dev build. Accepted tradeoff: push notifications must be hand-built via a Supabase Edge Function (no managed push service); implementation approach is ticket 18. EU-region hosting locked as a build constraint, specifics deferred to ticket 15.
- [Friend discovery/onboarding mechanism](issues/16-friend-discovery-onboarding-mechanism.md): Personal reusable Invite Link (supports invite-to-install) + exact-handle-only search for MVP; contacts sync deferred to post-MVP. Explicit accept always required, even via Invite Link. Skippable "invite a friend" screen right after signup, not an onboarding gate. New vocabulary: Handle, Invite Link (see CONTEXT.md).
- [GDPR technical policy decisions](issues/15-gdpr-technical-policy-decisions.md): Deletion window for the temporary cloud copy is 48 hours (or on confirmed download, whichever sooner) — revised from an initially-locked 24 hours during ticket 11's session; provider-managed AES-256 at rest, TLS floor via iOS App Transport Security; EU region locked to Ireland (`eu-west-1`); deletion via a scheduled Edge Function through the Storage API (no native TTL exists); consent captured via a signup ToS click, just-in-time contacts prompt, in-app mic acknowledgment, and an explicit `consent_log` table — no marketing consent point yet (no marketing comms in MVP). Surfaces new schema requirements for ticket 10.
- [Audio recording constraints](issues/13-audio-recording-constraints.md): AAC-HE, mono, 44.1kHz, 32kbps, 30-second max duration (~120KB worst-case file size) — prioritizes transfer size/speed over marginal quality, since a slow/failed download degrades to the same fallback ticket 04 already handles.
- [Push notification implementation approach](issues/18-push-notification-implementation-approach.md): Direct APNs via a Supabase Database Webhook → Edge Function (own `.p8` key, hand-rolled ES256 JWT + raw HTTP/2 POST) — no third-party push vendor (OneSignal etc.), no FCM-for-push-only either, despite Supabase's own docs favoring FCM to avoid hand-rolling APNs. Best-effort/fire-and-forget (no retry). Two notification types: new Alarm Call received (this ticket), and Share-expired-undownloaded to both sender and recipient (added by ticket 11). Surfaces a device-token storage requirement for ticket 10.
- [Minimum supported iOS version](issues/17-minimum-supported-ios-version.md): iOS 26+ hard minimum, no degraded fallback for pre-26 devices — the only pre-26 wake mechanism (plain local notifications) undermines the core reliability promise worse than not installing at all. See [ADR-0001](../../docs/adr/0001-minimum-ios-26.md).
- [Data model schema](issues/10-data-model-schema.md): Concrete Postgres/Supabase schema for `profiles`/`friend_connections`/`alarms`/`alarm_calls`/`shares`/`queue_entries`/`library_entries`/`device_tokens`/`consent_log`. Shares fan out to every current Alarm rather than one designated receiving Alarm (see [ADR-0002](../../docs/adr/0002-shares-fan-out-to-every-alarm.md)); temp-copy tracking lives directly on `shares` (each Share gets its own `storage_path`, per ticket 11); Library is one unified table; device tokens upsert-reassign on reuse; Friend Connection is a single status-enum row; the Queue's "locked" property is server-enforced via a claim-time RPC, while download/prefetch itself stays unrestricted to satisfy ticket 06's offline-reliability need.
- [Alarm sharing / transfer mechanism](issues/11-alarm-sharing-transfer-mechanism.md): Presigned Storage URLs, Edge Function-minted (`createShare`, `getShareDownloadUrl`), no relay endpoint. Each Share gets its own server-copied Storage object (not the reused `alarm_calls.storage_path`), so one Share's 48h expiry/deletion can never affect another Share of the same reused Alarm Call. Download is layered/best-effort from the moment a Share is queued (push arrival, app foreground, AlarmKit callback) and fully decoupled from ticket 10's fire-time `claim_queue_head` gate; an undownloaded head falls back to ticket 04's default tone without being marked played, so it can retry on the next fire. On 48h expiry: cleanup deletes the Share, both sender and recipient get a push (new ticket-18 notification type), and the sender can manually re-Share — no auto-resend. Revised ticket 15's window from 24h to 48h.
- [Onboarding flow screens prototype](issues/19-onboarding-flow-screens-prototype.md): "Inline Minimal" screen structure chosen (compact single-column invite screen, Skip in the nav bar) with a more prominent-but-clean Invite Link treatment than the prototype's original bare icon. The pending-request accept step is conditional: shown only when the new account resolved a pending inviter via an Invite Link tap (ticket 16's invite-to-install mechanism) — organic signups skip that step entirely, and at most one resolved request can exist at that point.
- [Snooze/dismiss interaction mechanic](issues/20-snooze-dismiss-interaction-mechanic.md): Snooze uses AlarmKit's native snooze `AppIntent`, always replaying the same already-claimed Alarm Call across every re-ring of a Wake Event (new vocabulary, see CONTEXT.md) — no Queue advance, no re-claim; settings fixed/global for MVP, per-Alarm configurability deferred. Dismiss only stops playback/cancels pending snooze (no queue/Library side effects); it's the signal that makes it safe for ticket 06's resync-on-mutation hook to prep the next occurrence. Mid-Wake-Event arrivals never interrupt the active ring/snooze. See [ADR-0003](../../docs/adr/0003-native-alarmkit-snooze.md).
- [Deployment/CI pipeline](issues/21-deployment-ci-pipeline.md): GitHub Actions auto-deploys Postgres migrations + Edge Functions on merge to `main` via the Supabase CLI, gated by one manual approval click; prod-only (no staging Supabase project), local Supabase CLI stack for pre-merge testing; secrets split between GitHub encrypted secrets (CI-time) and Supabase's own secrets store (runtime); ticket 15's cleanup job runs via Supabase's native Scheduled Edge Functions. iOS app build/TestFlight distribution explicitly out of scope for this ticket.
- [iOS app build & TestFlight distribution](issues/22-ios-app-build-testflight-distribution.md): Xcode Cloud, manually triggered (not per-merge); External TestFlight testers (one-time Beta App Review on the first build); code signing fully automatic and managed inside Xcode Cloud (no certs/keys to store); build number auto-incremented by Xcode Cloud, marketing version bumped manually.

## Out of scope

- Post-MVP features: premium alarm packs, subscription tiers/monetization mechanics, challenge-based features, alarm analytics/insights, virtual gifts. Ruled out during destination-naming — this map targets the MVP only.
- Android — deferred to a future effort; this map is iOS-only.
- Legal document drafting (actual privacy policy / ToS text) — only the technical requirements those documents will need are in scope (see tickets 14, 15); drafting is a legal deliverable.
- Branding/visual design (name, visual identity) — doesn't shape the architecture decisions this map exists to make.
- Alarm-content discovery/browsing (e.g. browsing premium sound packs) — a Post-MVP monetization concern; see ticket 05.
- Phone-contacts sync for friend-finding — deferred to post-MVP; the GDPR consent UX plus server-side contact-hashing/matching wasn't worth the engineering cost for this 4-week solo build. See ticket 16.
- Interactive/gamified dismiss interaction (e.g. a friend can reposition or shrink the recipient's dismiss button to make waking harder/more playful) — a post-MVP engagement idea surfaced while resolving ticket 20; not part of the MVP dismiss mechanic (dismiss just stops playback).
