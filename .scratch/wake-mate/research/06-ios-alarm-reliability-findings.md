# iOS Alarm Reliability Research: Can Wake Mate Play a Specific Local Audio File at a Precise Scheduled Time?

## TL;DR

- **Yes, but only via one specific mechanism: Apple's `AlarmKit` framework (iOS 26+).** This is the framework Apple built at WWDC 2025 explicitly to solve "alarm-clock apps need to reliably fire a loud, custom sound even when silenced/backgrounded/force-quit," which was previously a Clock-app-only capability. It requires no restricted/Apple-approved entitlement — just an `NSAlarmKitUsageDescription` Info.plist key and runtime user authorization, the same pattern as HealthKit/Contacts-style permissions. Since Wake Mate is iOS-only and this is a fresh MVP, this should be the primary mechanism, not a legacy workaround.
- **All the older approaches have real, documented gaps for this exact use case:**
  - **Background execution APIs** (Background App Refresh, `BGTaskScheduler`) are explicitly *best-effort, not guaranteed-time*, and are **entirely blocked** once a user force-quits the app (swipes it away in the app switcher) until the user manually relaunches it. Silent push is similarly best-effort/throttleable and is blocked outright if the app was force-quit.
  - **Critical Alerts** (`com.apple.developer.usernotifications.critical-alerts`) do bypass silent mode/Focus/Do Not Disturb, and *do* require a restricted entitlement Apple must approve (health/safety/security use cases). But critically: **the sound is still a bundled short audio file subject to the same ~30-second custom-sound duration limit as ordinary notification sounds** (looping is possible but it's the same short clip looping, not one long arbitrary file). It is not a general-purpose "play this exact 90-second voice memo" mechanism, and a social/friend-alarm app is a poor fit for the approval criteria anyway (Apple's form targets health, safety, home-security categories).
  - **Time-Sensitive/critical local notifications** (`UNNotificationRequest` + `UNCalendarNotificationTrigger`) have the same ~30-second custom sound ceiling, and the sound file must already be present in the app bundle/container and referenced by name **at the moment the notification is scheduled** — it cannot be swapped for a different file by live app code at fire time if the app isn't in the foreground, because the OS (not your process) plays it.
  - **The classic "silent/looping background audio" keep-alive trick** used by apps like Alarmy predates AlarmKit and works by declining to ever let the process suspend (`UIBackgroundModes: audio`), so *live app code* — not a baked-in notification sound — decides what file to play at the exact right moment. It is real, in production, and has weathered App Store review (Guideline 2.5.4 requires background modes be used for their "intended purpose"; Apple has pushed back on this exact pattern for AlarmKit-eligible alarm apps in review, per public discussion), but it is now the *legacy* solution AlarmKit was built to make unnecessary.
- **The queue/schedule-time conflict is real but manageable, not a fundamental blocker.** Both the notification-sound approach and (to a lesser degree) AlarmKit bake the sound selection in at schedule time, not fire time — there is no "decide the file at the exact moment the alarm rings" hook when the app isn't already running live in the foreground/audio-session-alive background. The practical answer for Wake Mate is **(a) reschedule/replace the alarm's sound reference every time the queue's head changes** (cancel + re-schedule, which AlarmKit and `UNNotificationRequest` both support as a delete+recreate operation, not an in-place mutation), triggered opportunistically whenever the app is briefly woken (foreground, launch, or a best-effort background/push wake) after a new Alarm Call arrives. This does **not** require ticket 03's locked-queue/auto-play mechanic to be redesigned, but it does mean the "when does the notification/alarm's baked-in sound get updated" step needs to be an explicit, idempotent operation that runs on every queue mutation, with a safe fallback (playing the *previous* queue head, which is still a valid, already-approved-for-that-slot Alarm Call) if a reschedule attempt is missed.

## 1. iOS Background Execution Limits

Apple's own developer-forum guidance (an Apple engineer's canonical explanation of background execution, widely cited across the developer community) states plainly that iOS provides no general mechanism for running code continuously, at specific times, or at guaranteed intervals in the background:

> "The system applies a range of heuristics to decide which apps get app refresh time and when... if you expect that the app refresh mechanism will grant you background execution time, say, every 15 minutes, you'll be disappointed. In fact, there are common scenarios where it won't grant you *any* background execution time at all!"
— [iOS Background Execution Limits — Apple Developer Forums](https://developer.apple.com/forums/thread/685525)

Key mechanisms and their guarantees:
- **`BGAppRefreshTaskRequest`** (small refresh work) and **`BGProcessingTaskRequest`** (longer processing, e.g. overnight) — both scheduled via `BGTaskScheduler` — are **best-effort**; the OS decides if/when to actually run them based on usage heuristics, battery, charging state, etc. There is no way to say "run at exactly 07:00." ([Apple Developer Forums](https://developer.apple.com/forums/thread/685525); [Background Tasks tag](https://developer.apple.com/forums/tags/backgroundtasks?page=7))
- **Silent (background) push notifications** ("resume your app in the background in response to an event on your server") are likewise throttled/coalesced by APNs and the OS, are not guaranteed to arrive promptly, and can be effectively deprioritized if the app doesn't handle them efficiently or if the user disables background refresh for the app. ([Apple Developer Forums](https://developer.apple.com/forums/thread/685525))
- **Force-quit is the hard wall.** When a user swipes an app away in the app switcher:
  > "If the app is running, iOS terminates it. iOS also sets a flag that prevents the app from being launched in the background. That flag gets cleared when the user next launches the app manually."
  — [Apple Developer Forums (iOS Background Execution Limits)](https://developer.apple.com/forums/thread/685525)
  This blocks **all** the general-purpose background-wake mechanisms above — background fetch/refresh, `BGTaskScheduler` tasks, and silent push — until the user manually reopens the app. Multiple independent forum threads confirm `BGProcessingTaskRequest`/background fetch do not fire after force-quit ([BGProcessingTaskRequest executing even after force-quit](https://developer.apple.com/forums/thread/793189), [Background fetch when app is forced quit](https://developer.apple.com/forums/thread/808088), [Handle background task in terminated app state](https://developer.apple.com/forums/thread/764572)).
  - **VoIP PushKit is not a reliable exception either**, despite older folklore. A developer specifically asking whether VoIP push could relaunch an app after force-quit (for a non-call BLE use case) was told by an experienced community member that iOS will stop delivering VoIP pushes to an app after a few pushes aren't properly reported to CallKit, and that using VoIP push as a generic "wake me after force-quit" mechanism for non-call purposes is both unreliable and an App Review rejection risk. ([Use VoIP to wake up App after force-killed — Apple Developer Forums](https://developer.apple.com/forums/thread/113185))
  - The narrow, genuinely documented exceptions to the force-quit wall are things like significant-location-change region monitoring and a small number of special-purpose system frameworks (not general BGTaskScheduler/background fetch/silent push). This confirms the brief's premise: **a force-quit app cannot reliably be "background-woken" by ordinary means to play a specific file at a specific time.**

**Bottom line for point 1:** none of the general background-execution primitives (BGTaskScheduler, background fetch, silent push) can be relied on to guarantee that app code runs at an exact wake time, and all of them are switched off entirely by force-quit. Any reliable solution has to route through a mechanism the OS itself treats as a first-class scheduled-alarm primitive (local notification triggers, or AlarmKit) rather than through "wake my process and let it decide."

## 2. Critical Alerts Entitlement

**What it is:** `com.apple.developer.usernotifications.critical-alerts` is a restricted entitlement. To use it you must:
1. Request authorization from the user with `.criticalAlert` included in `UNAuthorizationOptions`. ([`criticalAlert` — Apple Developer Documentation](https://developer.apple.com/documentation/usernotifications/unauthorizationoptions/criticalalert))
2. Have Apple grant your app the entitlement via a special request form: `https://developer.apple.com/contact/request/notifications-critical-alerts-entitlement`. ([Critical Alerts — Apple Developer Documentation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.usernotifications.critical-alerts))

**Approval scope:** Apple's stated purpose for this entitlement is narrowly health/safety/security-oriented (the request form and community reports consistently describe it as intended for things like medical alert apps, home security, and public-safety notifications — see e.g. a doctor specifically asking about eligibility: [Critical Alerts App for doctors — Apple Developer Forums](https://developer.apple.com/forums/thread/773648)). A social "friends send you a wake-up voice clip" app is a materially weaker fit for this category than a genuine alarm-clock app, and even alarm-clock apps historically had to justify use carefully.

**What it actually enables — and the critical nuance the brief asked to verify:** Critical Alerts bypass Do Not Disturb, Focus modes, and the mute/silent switch, and ignore the user's per-app notification settings. **However, the sound is still a notification sound, not an arbitrary long audio file.** Apple's API for this is `UNNotificationSound.criticalSoundNamed(_:withAudioVolume:)`, which — like ordinary custom notification sounds — must reference a short audio asset (CAF/AIFF/WAV format) bundled with the app, and is governed by the same **~30-second custom-sound duration ceiling** applied to all `UNNotificationSound` custom sounds. The "critical" designation changes *whether the sound plays despite silence/DND/volume* and adds louder/insistent playback and a special critical-alert icon; it does **not** lift the duration limit or let you point it at an arbitrary long recorded clip. Practically, developers get around this only by looping a short clip, which is not the same as playing one specific longer file (e.g. a 60–90 second Alarm Call) start-to-finish as recorded.

## 3. Time-Sensitive / Critical Local Notifications

`UNMutableNotificationContent.interruptionLevel` supports `.active` (default), `.passive`, `.timeSensitive`, and `.critical`. `.timeSensitive` presents the notification immediately, can light the screen, and is designed to break through Focus filtering (users can still allow/deny per-app), but — unlike `.critical` — it **does not** bypass the mute switch or Do Not Disturb on its own, and it still uses an ordinary custom `UNNotificationSound` (same ~30-second limit). `.critical` requires the Critical Alerts entitlement from section 2. ([`UNNotificationInterruptionLevel.timeSensitive` — Apple Developer Documentation](https://developer.apple.com/documentation/usernotifications/unnotificationinterruptionlevel/timesensitive))

Scheduling mechanics relevant to Wake Mate:
- A local notification is a `UNNotificationRequest` composed of content + a trigger (`UNCalendarNotificationTrigger` for a specific date/time — the natural fit for a scheduled Alarm — or `UNTimeIntervalNotificationTrigger` for a relative delay), added via `UNUserNotificationCenter.current().add(request:)`. ([Scheduling notifications — Hacking with Swift](https://www.hackingwithswift.com/read/21/2/scheduling-notifications-unusernotificationcenter-and-unnotificationrequest))
- **Custom sound files must be ≤ ~30 seconds and in CAF/AIFF/WAV format**, bundled in the app (or its container) ahead of time. This 30-second ceiling is a hard, consistently-documented OS limit for both ordinary and critical custom notification sounds — confirmed across Apple's own API docs and multiple independent developer write-ups. ([`UNNotificationSound` — Apple Developer Documentation](https://developer.apple.com/documentation/usernotifications/unnotificationsound); community confirmation via [UNNotificationSound not playing custom sound — Apple Developer Forums](https://developer.apple.com/forums/thread/49512))
- Since Wake Mate's Alarm Calls (friend-recorded voice clips) can plausibly run well past 30 seconds, a bare local-notification-with-custom-sound cannot play a full Alarm Call as recorded — at best it could play a truncated/looped teaser, with the *actual* full clip played only once the app is opened (foreground) after the user taps/wakes.

## 4. How Existing Alarm Apps Solve This in Practice

### 4a. The legacy pattern (pre-AlarmKit, still in use by apps predating iOS 26 or targeting older OS versions)

The common architecture reported by developers and reflected in production apps like Alarmy:
1. Schedule a local notification (often Time-Sensitive) for the exact alarm time as a backup/fallback.
2. Declare `UIBackgroundModes: audio` in Info.plist and keep an `AVAudioSession` continuously active (historically via a looping low-level ambient/ticking sound, sometimes effectively silent), which prevents the OS from ever fully suspending the process. Because the process stays alive, **live app code** — not a static, pre-baked notification sound — is what decides which file to play and can present a full-screen custom alarm UI at the precise scheduled instant, including playing an arbitrary-length custom audio file (a friend's Alarm Call, in Wake Mate's case).
3. Because the audio session keeps the app "resumable," when the exact wake time arrives the app's own timer/logic fires and swaps in the real, chosen audio.

Real-world confirmation and known behavior:
- Alarmy's own published behavior: "When Alarmy is removed from the background, the app will send endless system notifications to replace the original alarm. Due to iOS policy, Alarmy cannot make a sound when both Alarmy is removed from the background AND your phone is in silence mode or Focus mode." This is a direct, documented admission that **the silent-audio/background-keep-alive trick does not survive force-quit** — it only helps while the app is merely backgrounded, not terminated. ([Alarmy App Store listing / reviews](https://apps.apple.com/us/app/alarmy-loud-alarm-clock/id1163786766))
- A widely-discussed GitHub thread for the popular Flutter `alarm` plugin documents real App Store review friction over exactly this pattern: reviewers challenged whether background audio was necessary ("Background audio intended for setting and playing alarms is inappropriate because it can be replicated with Local Notifications" — Guideline framed under background-modes misuse), developers pushed back that local notifications can't play extended audio and are suppressed under DND, cited Alarmy as precedent, and ultimately got apps approved after detailed justification of the audio-session approach as functionally necessary. The thread explicitly flags **AlarmKit as the forward-looking replacement** for this whole workaround once iOS 26 adoption is high enough. ([About App Store Guidelines · gdelataillade/alarm · Discussion #87](https://github.com/gdelataillade/alarm/discussions/87))
- Apple's own guidance is consistent with this tension: "Background audio is intended for use by apps that provide audible content to the user while in the background, such as music player, music creation, or streaming audio apps," and the App Store Review Guideline governing this is **2.5.4**: "Multitasking apps may only use background services for their intended purposes: VoIP, audio playback, location, task completion, local notifications, etc." — meaning declaring `audio` background mode without genuinely providing audible content is itself a review risk (Apple actively checks for apps that declare the audio background mode as a life-support hack rather than delivering real audio content). ([App Store Guidelines mirror](https://github.com/saniul/AppStoreGuidelines/blob/master/App%20Store%20Guidelines.txt); [UIBackgroundModes discussion — Apple Developer Forums](https://developer.apple.com/forums/thread/47368))
- Community consensus (including an unanswered, multi-year-old Apple Developer Forums thread where a developer explicitly asks how apps like Alarmy/Sleep Cycle achieve indefinite background sound and gets no authoritative answer) is that this behavior was always somewhat fragile/undocumented and dependent on continuous non-silent audio playback, not a supported "keep my process alive forever" API. ([Playing scheduled alarm sounds while app is in background — Apple Developer Forums](https://developer.apple.com/forums/thread/724742))

### 4b. The modern, Apple-sanctioned pattern: AlarmKit (iOS 26+)

At WWDC 2025, Apple shipped **AlarmKit**, a framework whose explicit purpose is to let third-party apps schedule alarms with the same system-level privileges previously reserved for the built-in Clock app — alerts that fire even in silent mode or under a Focus, full-screen Lock Screen/Dynamic Island/StandBy presentation, and Apple Watch mirroring — "no longer relying on background tricks or hoping notifications do the job." ([Wake up to the AlarmKit API — WWDC25, Apple Developer Videos](https://developer.apple.com/videos/play/wwdc2025/230/); [iOS 26 Makes Third-Party Alarm and Timer Apps Better — MacRumors](https://www.macrumors.com/2025/06/11/ios-26-third-party-alarm-apps/))

Key technical facts gathered from Apple's docs and independent developer testing:
- Core types: `AlarmManager` (authorization, scheduling, snoozing, cancelling), `AlarmAttributes`/`AlarmPresentation` (UI), `AlarmConfiguration` (schedule + sound + snooze + `AppIntent` stop/snooze actions). ([AlarmManager](https://developer.apple.com/documentation/alarmkit/alarmmanager), [AlarmAttributes](https://developer.apple.com/documentation/alarmkit/alarmattributes))
- Authorization is the ordinary "usage description + runtime prompt" pattern (`NSAlarmKitUsageDescription` in Info.plist, `AlarmManager.requestAuthorization`), **not** a restricted/Apple-approved entitlement. A confirmed Apple Developer Forums thread shows a developer hitting a provisioning-profile error for a nonexistent `com.apple.developer.alarmkit` entitlement; the resolution (an Apple engineer's guidance) was that **this entitlement does not exist at all** — it was an LLM-hallucinated requirement, and removing it fixed the build. AlarmKit needs only the Info.plist usage string, no special capability grant. ([Provisioning Profile Missing com.apple.developer.alarmkit Entitlement — Apple Developer Forums](https://developer.apple.com/forums/thread/797950))
- Alarms fire even when the app is fully terminated — the underlying mechanism is a system daemon (`mobiletimerd`, part of `MobileTimer.framework`, the same private infrastructure the Clock app itself uses) that tells SpringBoard to present the alarm UI independent of the app's process state; the app is only launched afterward, when the user interacts with the alert. ([My ADHD vs. the AlarmKit API — Jacob Bartlett](https://blog.jacobstechtavern.com/p/adhd-vs-alarmkit))
- Custom sounds: supported via `AlertConfiguration.AlertSound.named(_:)`, referencing a sound file in the app's main bundle (Library/Sounds container support was unreliable in early betas). However, **the same ~30-second custom-sound duration ceiling applies** — multiple independent developers confirm custom AlarmKit sounds must be under 30 seconds, and that (as of testing through iOS 26 betas) custom sounds **play once and do not loop** by default, unlike the Clock app's own repeating alarm tone. ([AlarmKit — Custom Sounds? — Apple Developer Forums](https://developer.apple.com/forums/thread/788836); [Alarmkit custom sound plays once](https://developer.apple.com/forums/thread/797172); [Alarm Kit - Sound Repetition](https://developer.apple.com/forums/thread/806697))
- There is **no in-place "update this alarm's sound" API** — to change an alarm's configuration (including its sound) you cancel/stop the existing alarm and schedule a new one with the desired configuration. AlarmKit does provide an async sequence that emits the current set of alarms whenever the system adds/removes/mutates one, useful for keeping local app state in sync. ([Scheduling Alarms in iOS Apps with AlarmKit — Medium](https://medium.com/@manavmanuprakash/scheduling-alarms-in-ios-apps-with-alarmkit-a-complete-guide-88b727f1c523))
- Minimum OS: iOS 26.0+. As of the current date (September 2026), iOS 26 has been shipping for roughly a year, so this is a reasonable baseline for a brand-new iOS-only MVP, though Wake Mate should decide its minimum-supported-OS policy explicitly since pre-26 devices get none of this.

**Tradeoffs/review risk comparison:** the legacy silent-audio-keep-alive trick carries real, documented Guideline 2.5.4 review risk and has a known, acknowledged failure mode (doesn't survive force-quit, and can be silenced by DND/mute in some app implementations per Alarmy's own disclosure). AlarmKit, being Apple's purpose-built replacement, carries essentially none of that review risk (it's meant for exactly this) but comes with the 30-second custom-sound ceiling and no in-place update — the same fundamental limitation as local-notification sounds, just packaged in a system-level, force-quit-surviving primitive instead of a Notification Center primitive.

## 5. The Queue/Schedule-Time Conflict — Verdict

**Question:** does any viable approach require finalizing the exact audio file to play *at schedule time* rather than *at fire time*, given that Wake Mate's per-Alarm queue head can change after the Alarm was originally scheduled (a new Alarm Call arrives overnight, after the notification/alarm was already scheduled with a specific sound file baked in)?

**Verdict: Yes, this is a real constraint — for every OS-mediated playback mechanism (local notification sound, Critical Alert sound, and AlarmKit alert sound alike).** In all three cases, the sound is a named file reference resolved and played by the OS/daemon, not decided by live app code at the instant of ringing, *unless* the app's own process is already alive and in control (the background-audio-keep-alive approach, or the moment the user actually opens/taps into the app). Concretely:
- `UNNotificationSound` must name a file already sitting in the app bundle/container at the time `UNNotificationRequest` is added to `UNUserNotificationCenter`; there is no dynamic "ask the app which file to play right now" callback for the notification sound itself when the app isn't foregrounded. (Section 3.)
- AlarmKit's `AlertConfiguration.AlertSound` is likewise fixed at `AlarmManager.schedule(...)` time, and there is no in-place mutation API — changing it means cancel-and-reschedule. (Section 4b.)
- Only the legacy background-audio-session approach lets *live app code* pick the file at the literal moment of ringing, because the process itself is what's doing the deciding and playing — but that approach doesn't survive force-quit and carries App Store review risk (Section 4a).

**Recommended workaround: (a), not (b).** Re-do the "schedule" step every time the queue's head changes, rather than trying to defer file-selection logic into fire-time app code:
1. Treat "schedule the Alarm's wake trigger" as an idempotent operation parameterized by *(fire time, currently-head-of-queue Alarm Call's local file)*, not a one-time action.
2. Every time the per-Alarm queue mutates (a new Alarm Call arrives and becomes the new head, or the current head is consumed/removed), re-run that operation: cancel the existing pending `UNNotificationRequest`/AlarmKit alarm for that Alarm and create a new one pointing at the new head's already-downloaded local file. Both AlarmKit and `UNNotificationRequest` are designed around delete+recreate rather than in-place mutation, so this is the natural, supported pattern rather than a hack.
3. This reschedule step should run opportunistically whenever the app has any execution window — app foreground/launch, a push-notification-triggered brief wake, or (for AlarmKit specifically) any point before the fire time, since AlarmKit persists independent of app state and only the *reschedule* operation needs the app briefly alive, not the eventual firing.
4. Provide a safe fallback for the case where a queue mutation happens overnight and no reschedule opportunity arises before wake time: since the *previous* head is already a valid, already-locked, already-downloaded Alarm Call for that slot, simply **do nothing and let the previously-scheduled alarm fire with the previous head's file** — this is a benign degradation (user hears a slightly "stale" but still legitimate queued Alarm Call), not a broken or empty state. This means Wake Mate does not need perfect reschedule delivery guarantees; eventual consistency across the (typically many-hour) window between a new Alarm Call arriving and the Alarm's fire time is sufficient in the overwhelming majority of cases.

**Does this require redesigning ticket 03's locked-queue/auto-play mechanic?** No. The locked-queue/FIFO/auto-play-head semantics described in the brief are unaffected — the queue's logical model (head is chosen automatically, previewing is locked) stays exactly as designed. What ticket 03's implementation needs to add is an explicit hook: *on every queue-head-change event, re-issue the scheduled wake trigger (notification or AlarmKit alarm) so its baked-in sound reference tracks the current head*, plus the fallback behavior above for the rare case where that hook doesn't get a chance to run before fire time. This is an implementation detail of "how the Alarm's wake trigger is kept in sync with the queue," not a change to the queue/locking model itself.

## Recommended Approach for Wake Mate

1. **Primary mechanism: AlarmKit (iOS 26+).** Schedule each user Alarm as an AlarmKit alarm via `AlarmManager`, with `AlertConfiguration.AlertSound` pointing at the local file for the current queue head. This gets Wake Mate the same system-level guarantees as the built-in Clock app: fires through silent mode/Focus, survives force-quit, full-screen Lock Screen/Dynamic Island presentation — without background-mode review risk, and without a restricted-entitlement approval process (only an Info.plist usage string).
2. **Respect and design around the 30-second custom-sound ceiling.** Since friend-recorded Alarm Calls will often exceed 30 seconds, don't rely on the OS-played alert sound to carry the *entire* clip. A practical pattern many alarm apps use conceptually: let the AlarmKit alert sound serve as the immediate "this is your alarm, wake up" cue (a short branded/teaser clip, ≤30s, chosen per-Alarm at schedule/reschedule time as described in Section 5), and use the AlarmKit alert's tap-through / app-launch behavior to bring the app itself into the foreground, where live app code with no duration limit plays the *full* Alarm Call from local storage via `AVAudioPlayer`. This sidesteps the 30-second limit entirely for the "real" listening experience while still getting a system-guaranteed wake trigger.
3. **Do not build the legacy silent-audio-background-keep-alive trick** as the primary mechanism for a new MVP — it's exactly the workaround category AlarmKit was introduced to retire, it doesn't survive force-quit anyway (per Alarmy's own disclosed limitation), and it invites Guideline 2.5.4 review scrutiny for zero net reliability gain over AlarmKit for a force-quit scenario. It may still be worth a *lightweight* supplementary background audio session while the app happens to be foregrounded/backgrounded-not-terminated, purely to make the in-app playback experience (item 2 above) more seamless, but it should not be load-bearing for the "survives force-quit" guarantee — AlarmKit already provides that.
4. **Use Time-Sensitive local notifications as a secondary/defense-in-depth signal, not the primary path** — e.g., a companion local notification at the same fire time (or slightly before, as a "your alarm is about to ring" heads-up) adds a system tray/lock-screen artifact independent of AlarmKit's own presentation, useful for platforms/OS-versions below iOS 26 or as a belt-and-suspenders redundancy, but it inherits the same 30-second/schedule-time-baked-in constraints as AlarmKit and doesn't add reliability beyond what AlarmKit already provides on iOS 26+.
5. **Skip Critical Alerts.** The approval bar (health/safety/security use cases) is a poor match for a social alarm-call app, and even if granted, it wouldn't remove the 30-second sound ceiling — AlarmKit gives Wake Mate everything Critical Alerts would have offered (bypass silent/DND/Focus) without the approval gate or the category mismatch.
6. **Explicitly decide and document a minimum supported iOS version.** AlarmKit requires iOS 26+; if Wake Mate wants to support pre-26 devices, it will need the legacy fallback path from point 3 for those users specifically, with the understood force-quit gap disclosed as a known limitation for that OS tier.
