# AlarmKit + React Native / Flutter Bridging — Research Findings

**Research date:** 2026-09-05
**Question:** Can a React Native or Flutter app on iOS call Apple's AlarmKit (iOS 26+) via a custom native module/plugin bridge, and how hard is that in practice?

Method note: Apple's developer.apple.com pages are JS-rendered SPA pages; several direct WebFetch attempts returned only the page `<title>` with no body content (flagged inline below each time this happened). Where that occurred, findings were cross-checked against a second/third independent source (another Apple URL that *did* render, a WWDC-session synthesis, or a named secondary article) before being reported as fact. Anything not independently corroborated is labeled as uncertain.

---

## 1. Existing plugins (React Native / Flutter wrapping AlarmKit)

**Bottom line: nothing official exists. What exists is a handful of very young, low-adoption community projects — none of them mature.** No plugin from Meta, Expo, the Flutter team, or Google was found. As expected for an API that shipped with iOS 26 (fall 2025), the ecosystem is thin as of Sept 2026.

### React Native
- **`rn-alarm-kit`** (wael-fadlallah) — [github.com/wael-fadlallah/rn-alarm-kit](https://github.com/wael-fadlallah/rn-alarm-kit). README carries an explicit warning: *"This library is currently under active development and is not yet production-ready"* and *"Use at your own risk in production environments."* 5 stars, 1 fork. iOS 26.0+ only; Android "planned for a future release." No mention of widget extension or App Intents support in its docs.
- **`@raphckrman/react-native-alarm-kit`** — [npmjs.com/package/@raphckrman/react-native-alarm-kit](https://www.npmjs.com/package/@raphckrman/react-native-alarm-kit). Requires `react-native-nitro-modules` (built on the Nitro Modules codegen system, not RN's classic bridge). WebFetch on the npm page returned HTTP 403 both times attempted, so package details (version, downloads, README specifics) could **not** be independently verified beyond the search-result snippet; treat its maturity as unknown.
- **`react-native-nitro-ios-alarm-kit`** (Gautham495) — [github.com/Gautham495/react-native-nitro-ios-alarm-kit](https://github.com/Gautham495/react-native-nitro-ios-alarm-kit). 79 commits, 12 stars, 0 forks, 1 open issue. Claims to work in both Expo and bare RN projects, iOS 26+ only, "requires physical device — simulator has limited support." No mention of widget extension or App Intents. No explicit "experimental" disclaimer, but the low star count and being built on the very new Nitro Modules system make its production-readiness unverified.
- A Medium post, *"How to Integrate Apple's AlarmKit with React Native (iOS 26)"* by Evinsta, bills itself as an early/first guide on this exact topic — [medium.com/@evinsta9/...](https://medium.com/@evinsta9/how-to-integrate-apples-alarmkit-with-react-native-ios-26-04afb13af59e). WebFetch on this URL returned HTTP 403 (Medium paywall/bot-block), so its content could **not** be verified directly — noted here only as evidence that at least one third party has written about attempting this, not as a source for technical claims.

### Flutter
- **`flutter_alarmkit`** (gdelataillade — the same author as the well-known `alarm` Flutter package) — [pub.dev/packages/flutter_alarmkit](https://pub.dev/packages/flutter_alarmkit), [github.com/gdelataillade/flutter_alarmkit](https://github.com/gdelataillade/flutter_alarmkit). This is the **most mature thing found in this entire investigation**, and it is still young: v0.4.0, published ~53 days before this research (≈mid-July 2026), 26 pub.dev likes, 978 downloads, 160 pub points. GitHub: 17 stars, 11 forks, 2 open issues, 51 commits. Requires Flutter 3.38.0+, Xcode 26+, an iOS 26+ device. Ships an automated setup command (`dart run flutter_alarmkit:setup`) that patches the Xcode project and scaffolds a dedicated WidgetKit target for the Live Activity. Calling AlarmKit APIs on iOS <26 throws a `PlatformException` with code `UNSUPPORTED_VERSION`.
- **`alarm`** (same author, [github.com/gdelataillade/alarm](https://github.com/gdelataillade/alarm)) is a separate, older, much more widely used general alarm plugin (audio-based, not AlarmKit-based) for iOS+Android; a GitHub Discussion on that repo (#87, see §3) shows the author was, as of that thread, still building the AlarmKit wrapper as a distinct, newer package rather than having folded AlarmKit support into the mature package.

**Assessment of this landscape:** ASSESSMENT (inference, not sourced) — `flutter_alarmkit` is the closest thing to a usable starting point, coming from a credible, experienced Flutter-plugin author, but at v0.4.x / <1,000 downloads / 2 open issues it is pre-1.0 and unproven at scale. Everything on the React Native side is smaller and newer still, with one explicitly self-labeled "not production-ready."

## 2. Technical quirks / packaging requirements documented by Apple

Confirmed (cross-checked across the WWDC session content, an Apple Info.plist reference page reachable via search snippet, and independent secondary corroboration):

- **Info.plist key — `NSAlarmKitUsageDescription` is required.** Apple's own reference page exists at [developer.apple.com/documentation/BundleResources/Information-Property-List/NSAlarmKitUsageDescription](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSAlarmKitUsageDescription) (direct WebFetch of this page returned only the title with no body — content below is reconstructed from independent search-result snippets of the same page, which is a weaker form of corroboration; treat the key's *existence* as confirmed, its exact wording as reasonably-but-not-fully verified). Without it, AlarmKit cannot schedule alarms and the OS will not show the authorization prompt.
- **No special entitlement is required.** This is an important, concrete finding: an Apple Developer Forums thread ([developer.apple.com/forums/thread/797950](https://developer.apple.com/forums/thread/797950), Aug 2025) shows a developer who added a fabricated `com.apple.developer.alarmkit` entitlement to their entitlements plist (apparently suggested by an LLM) and got a provisioning-profile build error because no such entitlement/capability exists in the Developer Portal. An Apple engineer (`kthchew`) replied that the fix is simply to **remove** the fake entitlement, and added: *"We are seeing an increase in LLMs making up non-existent entitlements causing similar problems — it has become a common occurrence,"* explicitly warning that LLMs conflate declared entitlements, capabilities requiring application, and Info.plist keys. **Net: AlarmKit's only declared "gate" is the Info.plist usage-description key plus runtime user authorization — not a provisioning-profile entitlement.**
- **Authorization is a runtime API, not a build-time capability.** `AlarmManager.shared.authorizationState` exposes `.notDetermined` / `.authorized` / `.denied`; `AlarmManager.shared.requestAuthorization()` is an async throwing call. Authorization can also be triggered implicitly the first time an alarm is scheduled. (Corroborated identically across the WWDC-session content, [developer.apple.com/documentation/alarmkit/alarmmanager/requestauthorization()](https://developer.apple.com/documentation/alarmkit/alarmmanager/requestauthorization()) — page existence confirmed by search, but direct WebFetch again returned only the title — and the secondary tutorial createwithswift.com.)
- **Core scheduling/cancel API is a plain async Swift API on `AlarmManager.shared`** — `schedule(id:configuration:)`, `stop(id:)`, plus cancel/pause/resume — callable, as shown in every source, directly from app code (SwiftUI view models, etc.), with no documented requirement to run inside a special process or extension. Page existence for `stop(id:)` confirmed at [developer.apple.com/documentation/alarmkit/alarmmanager/stop(id:)](https://developer.apple.com/documentation/alarmkit/alarmmanager/stop(id:)) (found via search; not independently re-fetched with full body). Community note (secondary, unverified against Apple docs directly): `stop(id:)` on a one-time scheduled alarm resets it to "scheduled" state rather than deleting it — `cancel` is what actually removes it. Since WakeMate's "queue-head reschedule" is described as cancel+recreate, this distinction between `stop` and `cancel` semantics is worth the team validating directly against Apple's docs/sample code before relying on it.
- **App Intents integration is required for custom Stop/secondary alarm buttons, but does not appear to require a separate extension target.** The WWDC session content shows a custom intent (conforming to `LiveActivityIntent`) defined as a plain Swift struct with `@Parameter` properties and an async `perform()`, referenced directly when building `AlarmConfiguration(... secondaryIntent: ...)`. In the sample shown, this struct lives in ordinary app code, not inside a separate extension.
- **A widget extension (WidgetKit target) is required specifically for the countdown/Live-Activity presentation path.** Multiple independent sources converge on this: (a) WWDC-session content states that if an alarm supports countdown behavior, a Live Activity — implemented as an `ActivityConfiguration` `Widget` — must be added to the app's widget extension; (b) a search-result synthesis of Apple/community material states plainly, *"AlarmKit expects a widget extension if an app supports a countdown presentation. Otherwise, the system may unexpectedly dismiss alarms and fail to alert"* and, separately, *"A widget extension is needed if an app will schedule anything with a CountdownDuration"*; (c) as concrete practical confirmation, the `flutter_alarmkit` plugin's own setup process scaffolds a dedicated WidgetKit target automatically, and its README notes custom tint-color UI requires an **App Group** so the widget extension and main app share the same UserDefaults suite.
- **For a pure scheduled "wake alarm" (not a countdown timer)**, I could **not** find an unambiguous, directly-quoted Apple statement definitively settling whether a widget extension/Live Activity is strictly mandatory versus optional-with-system-fallback-presentations. The WWDC content does describe "system fallback presentations" (`AlarmPresentation.Alert`, etc.) for when a Live Activity can't be shown (e.g., after a restart), which suggests non-countdown alert-only alarms may be able to rely on system presentations without a full custom Live Activity — but as of 2026-09-05 I could not confirm this distinction against Apple's own docs page content directly (the scheduling-guide page did not render body text for WebFetch). **This is a real open question the WakeMate team should resolve directly against Apple's sample code/docs before assuming a widget extension can be skipped.**
- **Platform scope:** AlarmKit is iOS/iPadOS/Mac Catalyst only (per a WWDCNotes.com secondary synthesis of the session) — consistent with it being irrelevant to Android entirely, which matches every RN/Flutter plugin found only supporting iOS.

## 3. Developer reports (forums, issues, Reddit, Stack Overflow)

**As of 2026-09-05, I could not find any substantive Reddit (r/reactnative, r/FlutterDev, r/iOSProgramming), Stack Overflow, or Apple Developer Forums thread specifically about bridging AlarmKit into a cross-platform RN/Flutter app.** This is consistent with AlarmKit being new and cross-platform bridging of it being a niche, early-stage activity. What was found:

- **Apple Developer Forums thread 797950** (Aug 2025, see §2) — a genuine early integration pain point (fabricated entitlement causing a provisioning-profile build failure), resolved by an Apple engineer. Not RN/Flutter-specific, but a real, dated, primary-source developer report about AlarmKit integration friction. [developer.apple.com/forums/thread/797950](https://developer.apple.com/forums/thread/797950)
- **GitHub Discussion `gdelataillade/alarm` #87** ("About App Store Guidelines") — [github.com/gdelataillade/alarm/discussions/87](https://github.com/gdelataillade/alarm/discussions/87). Not about AlarmKit directly (it's about the older audio-background-mode approach used by the `alarm` package), but relevant context: developers report repeated App Store rejections when using `UIBackgroundModes: audio` to keep alarm apps alive, with Apple reviewers arguing this should be handled with local notifications instead — a stance developers dispute because local notifications can't play long custom audio or reliably break through Do Not Disturb. Some developers eventually got approved after explaining their use case. In this same thread, the package author mentions **already building a separate AlarmKit-based Flutter wrapper**, noting adoption is "limited... since the technology isn't yet widely available across devices" (i.e., only iOS 26+ devices).
- A Medium article specifically framed as a React Native + AlarmKit integration guide exists (Evinsta, linked in §1) but its content could not be fetched/verified (403 response).
- No confirmed reports, positive or negative, of anyone shipping a production RN or Flutter app that uses AlarmKit through a custom bridge were found.

**Plainly stated: the developer-report evidence base for this exact cross-platform-bridging question is very thin — essentially one adjacent forum thread and one adjacent (pre-AlarmKit) App-Store-review discussion, not a body of direct experience reports.**

## 4. Effort / risk assessment for a solo/small-team 4-week MVP

### What is established fact (with citations, summarized from §§1–3)
- No mature, official, or widely-adopted RN/Flutter plugin wraps AlarmKit today; the best option (`flutter_alarmkit`) is a sub-1.0, ~2-month-old, <1,000-download package from an independent author, and RN alternatives are smaller/newer/self-described as not production-ready.
- AlarmKit's declared build-time requirements are comparatively light: one Info.plist key (`NSAlarmKitUsageDescription`), no special entitlement, a runtime authorization call.
- A widget extension (separate WidgetKit target, plus an App Group to share data with the main app) is required at least for the countdown/Live-Activity presentation, and the one community Flutter plugin found automates scaffolding that extra Xcode target as part of its install.
- App Intents (for custom stop/snooze buttons) can be defined as ordinary Swift structs without necessarily needing a separate extension target.
- No confirmed App Store rejections specific to AlarmKit usage were found either way.

### ASSESSMENT (inference, not sourced) — effort and risk
- Writing the Swift glue for the *core* operations WakeMate needs — schedule, cancel, stop, authorizationState, and a cancel+recreate "queue-head reschedule" — is, in isolation, a moderate, learnable amount of native-module code: the API surface is small and async/await-friendly, comparable in *raw bridging effort* to wrapping any other modern Swift framework via RN's Swift native-module bridge (or Nitro Modules) or Flutter's Swift platform channels. On its own this could plausibly be "a few days to a week" of glue code for someone comfortable in both Swift and the bridge mechanism.
- However, the **real schedule risk is structural, not glue-code volume**: standing up and correctly wiring a WidgetKit extension target (with an App Group) *inside* an RN or Flutter iOS project is materially harder than it sounds from either framework's own tooling — neither RN's nor Flutter's standard project templates or CLIs manage multi-target Xcode setups natively. The fact that the one semi-mature Flutter plugin found had to ship a custom `setup`/`--doctor` script to patch the Xcode project for exactly this reason is concrete evidence this is a real, nontrivial piece of engineering, not routine module glue. If WakeMate is on Expo's managed workflow, this very likely forces a move to a custom dev client / prebuild config plugin or bare workflow — extra setup and maintenance surface of its own.
- Because no mature reference plugin exists to copy from with confidence, the team would be debugging force-quit-survival and reschedule-reliability behavior — the app's core promise — through a brand-new bridge layer with no prior art, rather than directly against Apple's own sample code and WWDC guidance. Bugs introduced in that bridge layer become bugs in the single mechanism the whole product depends on.
- App Store review risk specific to AlarmKit is currently undocumented either way; ASSESSMENT (my own reasoning, not evidence): using Apple's own sanctioned alarm framework should, if anything, reduce review risk compared to older background-audio workarounds (per the friction visible in the `alarm` package's Discussion #87) — but this is inference, not something Apple or any developer report confirms yet, since AlarmKit is too new for a track record either way.
- **Net recommendation-relevant conclusion (ASSESSMENT):** for a 4-week MVP where AlarmKit-based reliability *is* the product's core mechanism, budget realistically for 1–2 of those 4 weeks going to bridge-layer and extension-target plumbing and debugging if going the RN/Flutter route, with a real (not just theoretical) chance of timeline overrun given the near-total absence of mature prior art to lean on. Building natively in SwiftUI avoids this entire category of risk by calling AlarmKit directly, using Apple's own sample code and the WWDC session as primary references, with no bridge layer between the app and the core reliability mechanism.
